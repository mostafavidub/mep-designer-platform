# Planha Semantic Dimension Engine Standard

**Status:** ACTIVE DESIGN CONTRACT  
**Rule:** `MEP-DIM-001`

## 1. Principle

A DXF `DIMENSION` entity is not, by itself, engineering meaning. Planha separates:

1. **Source Dimension Evidence** — what the consultant/source file said and measured.
2. **Semantic Dimension Intent** — what construction information the issued drawing requires.
3. **Rendered Dimension Entity** — the final CAD representation.

The flow is:

`Source DXF -> SourceDimensionRegistry -> Semantic references -> Drawing profile -> Dimension intents -> Minimal set-out set -> Placement -> DXF -> Exact reopen QA`.

Dimensioning is downstream of final geometry. It must never change routing, sizing, equipment selection or calculation authority.

## 2. Source preservation

No source dimension with geometric, construction, regulatory or coordination value may be silently destroyed. Every source dimension records, independently:

- entity identity and source layer/style;
- geometric measurement;
- displayed text/numeric override;
- type/orientation;
- extension reference points;
- semantic reference binding when proven;
- purpose/criticality;
- preservation policy.

Policies are `REGENERATE`, `PRESERVE_AS_EVIDENCE`, and `FLAG_CONFLICT`. Visibility is a separate drawing-profile decision; therefore suppression from a view never changes the preservation policy.

Suppression from a Mechanical view is not deletion from project knowledge.

## 3. Overrides and conflicts

Displayed text is never numeric source of truth. Geometry and displayed values remain separate.

Numeric source text is classified against the **literal precision actually displayed**. A value is formatting-equivalent only when the geometric measurement lies inside the half-unit rounding interval implied by the displayed decimal places; otherwise it remains an explicit numeric override for review. This is a drafting-consistency rule, not an engineering/code tolerance, and it never changes the geometry-derived engineering value. A contradiction such as 5.95 geometry displayed as 7.00 remains a conflict. Zero geometric dimensions and material numeric overrides require review before a Submission Ready claim. Non-numeric drafting text is preserved as evidence and is not converted into a design number.

## 4. Dimension purposes

Planha recognizes at least:

- PROPERTY / SETBACK
- BUILDING_OVERALL
- GRID
- STRUCTURAL_SETOUT
- WALL_SETOUT
- SHAFT
- STAIR_CORE
- OPENING
- CODE_CLEARANCE
- MECHANICAL_DATUM
- SETOUT
- CHECK

Unknown source dimensions are preserved conservatively.

## 5. Mechanical drawing profile

Architectural dimensions are not repeated wholesale. Existing source Grid/Overall/Core/Shaft information remains architectural evidence. Planha-owned Mechanical dimensions are generated only when a construction-critical object is not otherwise intrinsically located.

Initial automatic set-out targets are stable vertical cores and equipment-class nodes from the final authoritative network model. Each generated dimension is bound to:

- a stable architectural datum;
- a final authoritative Mechanical entity ID;
- an orientation;
- an engineering value;
- the drawing/board identity.

Fixture-by-fixture and furniture dimensions are not generated by default.

## 6. Determinacy and redundancy

The desired dimension network is:

**Minimal Set-out Graph + Intentional Check Dimensions**

Exact duplicate reference definitions are removed. Mandatory set-out dimensions are retained. A check/overall dimension may intentionally be redundant when it verifies closure or total geometry.

## 7. Placement

Dimension placement is a presentation operation after engineering intent is fixed. Generated plan dimensions are tiered by axis and board. Placement failure may never change the measured engineering value or reference identities.

## 8. QA

The semantic dimension gate verifies:

- source-dimension preservation;
- geometric/displayed-value separation;
- source conflict review;
- valid semantic references;
- mandatory set-out coverage;
- duplicate/redundant definition control;
- exact rendered identity;
- exact-file reopen;
- generated engineering value identity.

A count such as `DIMENSION > 0` proves only CAD inventory. It never proves engineering dimension completeness.

## 9. Units

DXF `$INSUNITS` is evidence, not absolute truth. Analyzer and Dimension Engine use the same pure Unit Sanity function to reconcile metadata with dimension plausibility. Each intent retains the native drawing measurement plus its canonical engineering value in metres and the unit-evidence source. Rendered set-out follows the issued drawing coordinate convention; the canonical metre value is retained separately for traceability. The Dimension Engine does not invent a conversion.

## 10. Source-reference corpus

Private customer/source drawings remain outside Git. They may be used as comparison evidence, never as hidden generation defaults. Synthetic tests cover source preservation, override conflicts, determinacy, generated Mechanical set-out and exact-file identity.


## 11. Final network reconciliation

The legacy CAD shell is not the engineering source of truth for final set-out. After the graph-native authoritative Mechanical network is materialized, Planha removes only its own provisional dimension entities, rebuilds set-out from the final authoritative network, and runs exact-file dimension QA again. Routing and sizing are never recomputed by the Dimension Engine.

## 12. CAD identity

Every Planha-owned dimension carries the registered DXF application identity `PLANHA_DIMENSION`. Regenerated source evidence is marked `SOURCE_DIMENSION`; Planha-created Mechanical set-out is marked `SEMANTIC_DIMENSION`. Source consultant entities are never reclassified as Planha-owned merely by layer name.


## 11. Governed compliance dimensions

`CODE_CLEARANCE` is never inferred from a visually similar gap. A compliance or Rule layer must provide an explicit requirement containing a Rule ID, two stable semantic references, actual geometry and a canonical `minimum_value_m`. Planha dimensions the actual designed geometry; the minimum is QA evidence. Missing Rule ID, unstable references, missing canonical minimum, or actual clearance below the minimum fails closed. This contract also supports explicit governed `OPENING`, `SETOUT` and `CHECK` intents without turning source-drawing recurrence into a design default.


## 11. Architectural-reference benchmark hardening

The six-project private reference corpus is comparison evidence, never a source of hidden project values. Aggregate benchmark facts used to test generality are:

- 835 source dimensions;
- 810 linear/rotated and 25 aligned;
- 16 numeric text overrides, 18 non-numeric overrides and 7 zero measurements;
- every reviewed file carried misleading `$INSUNITS=4` metadata while dimension plausibility resolved the working geometry to metre drawing units;
- repeated dimension baselines and chained adjacency are common, confirming that professional drawings use structured dimension networks rather than independent nearest-line labels.

These observations do **not** become numeric design defaults.

### 11.1 Raw source entity vs preserved source knowledge

A consultant `DIMENSION` is never copied blindly into a Mechanical board. Its evidence is first captured in the `SourceDimensionRegistry`. The Mechanical drawing profile then decides whether the dimension is regenerated, suppressed in the view, or blocked for review.

This prevents duplicate raw+Planha dimensions while preserving the original handle, geometry, style, displayed text, override status and semantic references.

### 11.2 Context completeness

Applicable plan profiles must not depend on the consultant having already drawn every useful dimension. When semantic geometry proves the required references and the equivalent source dimension is absent, Planha may generate:

- consecutive structural Grid spacing;
- Building Overall dimensions between proven opposite envelope faces;
- Shaft dimensions;
- Stair/Core dimensions.

Generated context dimensions use only the current project's semantic geometry and unit evidence. They are not inferred from reference-project sizes.

### 11.3 Source snapshot isolation

The architectural source entity set is frozen before board composition begins. Entities created for earlier generated boards may never be reclassified as source architecture for later boards.

### 11.4 Placement obstacles

Dimension text placement must consider architectural and mechanical presentation obstacles, including room text, MTEXT, block inserts, arcs and circles carried into the target board. Dimension-vs-dimension collision checks alone are insufficient.

If no collision-free candidate exists, the dimension gate fails closed rather than moving or changing the engineering measurement.

### 11.5 Remaining architectural-discipline boundary

The current Mechanical profile implements professional context plus Mechanical set-out. Full autonomous Architectural dimension-chain synthesis for every partition, opening, stair flight, room and site condition belongs to the Architecture discipline phase and must use the same semantic contract rather than introducing a parallel engine.
